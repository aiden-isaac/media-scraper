# Implementation Plan: Localhost GUI

**Branch**: `002-local-gui` | **Date**: 2026-06-22 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/002-localhost-gui/spec.md`

## Summary

Add a FastAPI-based web GUI that wraps the existing media-scraper pipeline. Users access it at `http://localhost:8000` where they can enter research topics, monitor scraper progress through phase updates, manage configuration (endpoint, model, output dir, max sources), and browse previously generated reports. The API key is never exposed in the UI. Only one scraper runs at a time. All existing pipeline logic is reused — this feature adds only the HTTP layer and web templates.

## Technical Context

**Language/Version**: Python 3.11+ (existing project requirement)

**Primary Dependencies**: 
- `fastapi>=0.104` — Web framework
- `uvicorn[standard]>=0.24` — ASGI server
- `python-multipart>=0.0.6` — Form data parsing
- `markdown>=3.5` — Markdown-to-HTML rendering for report preview

**Storage**: File system — config.toml for settings, reports/ for generated reports

**Testing**: pytest (existing test infrastructure); new tests go under `tests/test_gui/`

**Target Platform**: Linux/macOS/Windows desktop — single-user local machine

**Project Type**: CLI tool augmented with optional web GUI

**Performance Goals**: Page load < 500ms; scraper progress updates within 2 seconds of phase change

**Constraints**: 
- No authentication or multi-user support
- Synchronous blocking for scraper execution (single-user local tool)
- API key never transmitted over HTTP or rendered in HTML
- Server binds to 127.0.0.1 by default (no external network exposure)

**Scale/Scope**: One concurrent scraper run at most; typical reports contain 5–12 sources with moderate content sizes

**Structure Decision**: Keep the GUI as part of the existing `media_scraper` package rather than splitting into a separate `frontend/` directory. The GUI is tightly coupled to the existing pipeline module, config system, and models. A flat structure within the package avoids unnecessary separation and keeps imports simple. Templates use Jinja2 which is lightweight and fits Python conventions.
